history. Read this before changing a feature; update it when a decision changes.

## Hosting & deployment (GitHub Actions → Vercel, GitHub Pages redirect)
- **Purpose:** Compiles an 8-language Jekyll static site alongside Node.js serverless API routes (`api/`), deploying the combined bundle (`_site/`) to Vercel (`la-s78.app`) while publishing a path-preserving redirect (`_deploy/migration.html`) to GitHub Pages (`gh-pages`).
- **Constraints:** Vercel deployments are built and pushed via CLI (`vercel deploy --cwd _site/`) inside GitHub Actions after Ruby scripts generate in-memory JS modules (`api/_generated_translations.js`, `api/_map_svg.js`, `api/_cities_data.js`, `api/_alliances_data.js`, `api/_font_data.js`; and, before the site build, `js/alliance-defaults.js`).
- **Must not change:**
  - Staging `api/` into `_site/` (in `_scripts/build.rb`) MUST run *after* `WorkboxInjector.run('_site')` so `api/` is deployed to Vercel without being scanned by Jekyll or precached by the service worker.
  - The Vercel project is connected to this GitHub repo (kept for PR comments), but `vercel.json` sets `git.deploymentEnabled: false`. The GitHub Actions CLI deploy is the **only** route to production: a Git-triggered deploy would publish the raw, unbuilt repo, without `_site/` or the generated `api/_*.js` modules.
- **Test site (done 2026-11-11):** the `dev` preview (dev.la-s78.app) has its own test Gist (`TEST_GIST_ID`) and never touches live data; see "Data storage". It still shares the Discord bot, which refuses test proposals.

## Multilingual content pipeline (`_source/` masters, Gemini translation)
- **Purpose:** Allows guides, UI strings, rules, and bot strings to be authored in English (`_source/*_en.md`), translated into 7 languages (`de`, `es`, `fr`, `it`, `ru`, `tr`, `uk`) via Gemini, committed as master files (`_source/*.md`), and segregated into Jekyll collections/data at build time.
- **Constraints:** Gemini API rate limits require cooldowns between language calls; translation only runs on `push` when a `*_en.md` draft file is present.
- **Must not change:**
  - Never edit generated files directly: `guides/<lang>/`, `collections/_guide_panes/`, `_data/<lang>/bot.yml`, `_data/<lang>/rewards.yml` and `api/_generated_translations.js`. They are rebuilt on every build from `_source/*.md`.
  - The other `_data/<lang>/` files (`content.yml`, `rules.yml`, `survival_battle.yml`, `ui.yml`) are **hand-maintained source files** committed to the repo. Edit them directly. `ui.yml` also receives guide titles and nav anchors injected by `_scripts/sync_ui_data.rb`, which only adds missing keys and never overwrites existing ones.
- **The tools' text (`_data/<lang>/tools.yml`, owner decision 2026-11-12):** the words the interactive tools write (dashboard, editors, cards, messages) live in `_data/en/tools.yml`, the only copy people edit, grouped in top-level **sections** (`common`, `dashboard`, `caravan`…). On every push to `main`/`dev`, `_scripts/translate_sections.rb` sends Gemini each section whose English changed (a fingerprint per section and language is kept in `_scripts/translation_state.json`), **the whole section at once** so wording stays consistent, one call per language, and writes `_data/<lang>/tools.yml`; the workflow commits them with `[skip ci]` before building. Text goes to Gemini and back as **JSON** (YAML broke on strings like French "Statut : Ouvert"). A reply is only saved if it keeps the English keys and every `{placeholder}`; otherwise that section keeps its previous text (English until it succeeds). Unchanged sections are never re-sent. It retries Gemini only 3 times, so a busy Gemini never holds up a deploy, and the commit step rebases before pushing in case a commit landed meanwhile. **Prompt rules (maintainer review):** informal "you" in German, Spanish and Italian (du/tú/tu), the polite UI form in French, Russian, Ukrainian and Turkish (vous/вы/ви/siz); buttons in the infinitive (imperative in Turkish); KvK, NAP, T10, R1–R5, UTC-2, GT, `[TAG]`s and Discord untranslated; the glossary in `_data/terminology.json`. Chest names are translated like any text (owner: the game translates them literally). **Plurals:** English has `_one`/`_other`; Russian and Ukrainian also get `_few` (2–4); `tn()` picks the language's form with `Intl.PluralRules` and falls back to `_other`. **Human fixes** go in `_data/translation_overrides.yml` (language → section → key, same `{placeholders}`), laid over the translation on every run so they survive re-translations; editing `_data/<lang>/tools.yml` directly would be lost. Sections: about 25–60 strings each. Pages use it as `{{ "dashboard.title" | t }}` (`_plugins/tool_strings.rb`, HTML-escaped) and scripts as `t('dashboard.title')`, `tn(key, n)` for singular/plural (`key_one`/`key_other`) and `th(key, { html })` for text around trusted HTML (`js/i18n.js`); a page lists the sections its scripts need in its front matter (`strings: [dashboard, charts]`, plus `common` always) and the layout puts them in the page as JSON. Anything not translated yet shows the English. Server error messages (from `api/`) are still English. Tools moved so far: the Alliance Dashboard (incl. charts, editor, Caravan Rotor, reward card); the nomination page, King's console, registration, calendar, rewards and the planners follow (leaders' tools first).
- **Updating translated text (maintainer):** for small wording or number fixes, edit all 8 language blocks in `_source/<name>.md` directly (or ask Claude to update all 8 in the PR). For a major rewrite, rename `_source/<name>.md` back to `_source/<name>_en.md` containing only the updated English; CI then regenerates all 7 translations on push.

## Site shell (Turbo navigation, PWA / service worker, themes)
- **Purpose:** Provides fast app-like navigation and offline caching for guides and schedules on mobile and desktop.
- **Constraints:** Service worker precache (`_scripts/workbox_precache.rb`) must stay under 20 MB (skipping files >512 KB and `mermaid.min.js`).
- **Must not change:** Shared assets (`/css`, `/js`, `/images`) live only at the site root (`_site/`), never duplicated under `/<lang>/`. Event listeners in frontend JS must be idempotent across `DOMContentLoaded` and `turbo:load`. `initApp` (js/main.js) runs on both `turbo:load` and `turbo:frame-render`, so element listeners are attached through `firstTime(el, key)`; map controls are bound only by `js/map.js` (guarded by `data-bound`). Any data inserted into HTML (names, titles, tags, colours, anything from the API, localStorage or a form) goes through `escapeHtml()` from `js/escape-html.js`; never put raw data into `innerHTML`.
- **Service worker (`sw.js`):** pages and shared files are precached; images cached on use; live data (`/api/state`, `/api/calendar`) fetched fresh and the last good answer kept for offline (see "Alliance defaults"). Offline, a page that was never saved opens the home page in the reader's language (looked up with `getCacheKeyForURL`, because precached files are stored under versioned addresses). Old caches are cleaned on update (`cleanupOutdatedCaches`).
- **Portal pages (owner decision, 2026-11-11):** the nomination page, the King's console and registration (`_layouts/portal.html`) show the site header, so people can see who they are and sign in there, but no footer. Signing in comes back to the same page, address and `?token=` included (`auth-return-path` in `js/main.js`; only paths on this site).
- **Stuck on an old version (maintainer spec, 2026-11-11):** pages from before the update toast (rebuilt 9 November 2026) never tell a new service worker to take over, so it would wait forever. Three fixes:
  - **Automatic:** a new `sw.js` first asks the open pages (`SW_UPDATE_AVAILABLE`). Current pages answer (`SW_TOAST_SHOWN`, `js/main.js`) and keep the usual toast; if none answers within 2 s, the new version takes over by itself (`skipWaiting`, `clients.claim`) and reloads those pages. The first install is untouched. `vercel.json` serves `/sw.js` with `no-cache, no-store`.
  - **`https://la-s78.app/reset`** (`_deploy/reset.html`, a plain page copied to `/reset.html` by the build and served at `/reset` by `vercel.json`, which also sends its headers; no serverless function, so a slot stays free on Vercel's Hobby plan): a link to post in Discord. It was never in any saved list, so even a stuck app fetches it; it removes the service worker and saved files (plus `Clear-Site-Data: "cache"` where supported), then opens the home page with a short "App updated" note. Its notice says it updates the **website** ("Last Asylum / Survival Compendium", owner decision), over Gemini's desk-scene art (`images/compendium-desk.webp`, 50 KB, kept out of the offline copy) recoloured per theme like the header lantern, from the saved `site-theme`. It stays on screen for at least 1.5 s (readable, not a flicker) and at most 4 s, even if the clean-up hangs (owner decision).
  - **Update App** in the header pill card (anyone with a card, guests included; signed-out visitors' pill goes straight to sign-in, so they use `/reset`). Same clean-up, then reloads the page.
  All three keep `localStorage`: the login pass, theme and planner drafts survive.
- **Installed app:** `site.webmanifest` has shortcuts (Map, Alliance, Calendar, Rules) that go through the root language redirect (`/?to=map` etc., `_deploy/redirect.html`), so they open in the reader's language. iOS uses `images/apple-touch-icon.png` (180 px). The 512 px icon serves as both normal and maskable: the lantern already sits inside Android's round crop (checked 2026-11-11).
- **To do (later):** the worker loads Workbox **4.3.1 (2019) from Google's CDN**. Bundle a current Workbox with the site instead (removes the outside dependency); its API differs (e.g. `workbox.expiration.Plugin` → `ExpirationPlugin`), so it is its own change, tested with a real service worker.
- **Offline languages (maintainer, 2026-11-11):** all 8 languages stay precached while the precache stays well under the 20 MB limit (9.2 MB in November 2026). Reconsider precaching only the reader's language if it nears about 15 MB.

## Authentication & roles (Discord OAuth, R4/R5/member, Stewards)
- **Purpose:** Restricts administrative actions, reward nominations, and calendar management to authorized leadership.
- **Constraints:** Kingdom-wide administrative approval and maintenance tasks are restricted to 1–3 designated **Kingdom Stewards** defined in Vercel environment variables (`STEWARD_USER_IDS`, comma-separated Discord User IDs, with fallback support for `AUTHORIZED_USER_ID`).
- **Must not change:** Steward user IDs must remain in Vercel environment variables (read-only at runtime), never stored inside the GitHub Gist JSON files. Official leadership communications and embeds use the term **NAP Leadership** (never "War Room"). Internal identifiers (e.g. the `WAR_ROOM_CHANNEL_ID` env var) are not user-facing and keep their names.
- **Also must not change:**
  - `.content-locked` is **decluttering only** (progressive disclosure for leaders), not a security boundary: anything inside it is public in the page source. Real access control lives server-side (`api/_tokens.js`, `isSteward()`, alliance-scoped calendar filtering). Never put secrets in locked content.
  - **Leadership permissions** (R5, R4, HR and the officer roles an alliance names with `/registerbot`) are matched by Discord **role names** (`@R5`, `@HR`, `@<TAG>`), deliberately not role IDs: each registered alliance server has its own role IDs, and matching is scoped to the registered `guild_id` (or the central NAP server). Don't replace this with hard-coded role IDs. (Finding *which alliance* someone is in may use the `DISCORD_<TAG>` role IDs in the NAP server, below: that grants nothing by itself, so it doesn't break this rule. Confirmed by the maintainer, 2026-11-11.)
- **Website ranks (owner decisions):** the login (`api/verify.js`) gives one of: *Guest* (not in the NAP Discord server: no login pass), *Member*, *R4*, *R5*; *Steward* is a separate yes/no on top. **Officers count as R4:** a Member whose alliance registered its own server with `/registerbot` and who holds one of that alliance's officer roles there (the `delegated_roles` it chose, R5, or Administrator) gets R4 access on the site, including sending proposals, exactly as the bot treats them. Bot and site share one rule, `api/_officer_roles.js`. If that server can't be reached, the person stays a Member. **Alliance at login:** first the alliance role IDs set in the environment, checking only the `DISCORD_<name>` settings listed under `role_settings` in `_data/alliances.yml` (so no other `DISCORD_*` setting can be taken for an alliance) and giving the alliance's real tag (`RÂVN`, not `RAVN`); if none matches, the role names in the NAP server, as the bot does (`WLO`, `[WLO]`, `@WLO`, for alliances in `map-state.json`); last, a `[TAG]` at the start of the server nickname when TAG is a known alliance. The alliance is for display and for finding the officer server; it grants nothing by itself.
- **Header sign-in pill (`js/identity-pill.js`):** the site's only general sign-in button. Collapsed it shows the avatar and rank badge only (a Steward gets the crown beside their alliance rank, and both badges in the card: Steward is shown as well as R4/R5/Member, not instead) (a name would run into the page subtitle; it's in the card and the tooltip). The card lists only what the site really does for that rank (kept in line with `api/proposal.js`), when the login pass expires, Refresh Access (Discord's `prompt=none`, no Authorize screen) and Sign Out. A non-Guest without a usable pass shows **Expired**, not signed in. Signing out clears the browser only: a copied pass keeps working until it expires (accepted trade-off, with the 5-a-day limit).

## Discord bot & proposal/approval flow (`api/interactions.js`, `api/proposal.js`, `api/_accept_proposal.js`)
- **Code layout:** `api/interactions.js` only checks Discord's signature and hands each command and button to its module through the `COMMANDS` / `BUTTONS` tables: `_bot_calendar.js`, `_bot_info.js` (`/sb`, `/rules`), `_bot_map.js`, `_bot_register.js`, `_bot_rewards.js` (`/nominate`, `/rewards`, Won/Lost), `_bot_rank.js`, `_bot_proposals.js` (Steward review). Shared pieces are in `_bot_common.js` and `_bot_roles.js`; the alliance-server command list is `_bot_schema.js`, the only copy. A handler that doesn't answer returns `NOT_HANDLED` (the request then gets 400, as before).
- **Purpose:** Powers slash commands (`/calendar`, `/nominate`, `/rewards`, `/map`, `/sb`, `/rules`, `/rank`, `/registerbot`) and interactive button approvals for map, standings, rewards, and defense overrides.
- **Constraints:** Discord interaction responses must complete within 3 seconds (Gist and Discord role fetches use strict `AbortSignal.timeout`).
- **Must not change:** Portal links are signed and checked only through `api/_tokens.js` (`createToken`, `verifyToken`). They are signed with a dedicated key: `PORTAL_HMAC_SECRET` if set in Vercel, otherwise a key derived from the bot token. Never sign with the raw bot token. Every portal link carries an `action` (`nominate`, `register`, `manage_events`) and each endpoint accepts only its own, since they are all signed with the same key. Only designated Stewards (`isSteward(userId)`) can click Approve/Reject on proposals or confirm KvK reward outcomes. Unauthorized clicks must return an ephemeral access-denied message without mutating the button state.
- **Open questions:**
  - **Done: blacklist proposals are separate (owner request).** On the Alliance page the top Submit Plan sends the standings only (type `alliance`, no blacklist); the blacklist's own Submit sends a "NAP Blacklist Proposal" (type `blacklist`) with only add/remove changes. A Steward's approval applies those changes to the blacklist as it is at that moment (letter case ignored), so proposals approved one after another don't undo each other, and standings approvals don't touch the blacklist. Standings proposals that still carry a whole blacklist (sent before this change) still save it.
  - **Done: `/api/proposal` requires a login pass (owner decisions).** At login, `/api/verify` gives members of the Discord server a signed pass (`createSessionToken` in `api/_tokens.js`: Discord id, server nickname, rank, alliance; **30 days**). The proposal pop-up sends it as `Authorization: Bearer`. `/api/proposal` accepts **R4 and R5 leaders and Stewards** only, shows the name from the pass as the submitter (with a Discord mention; the page's `submittedBy` is ignored), rejects oversized or malformed proposals, and limits R4/R5 to **5 proposals per 24 hours** (Stewards: no limit), counted in the Gist's `proposal-log.json` only once a proposal was actually posted. If that log can't be read, nothing is sent (503). Login passes are signed with their own derived key, so a pass is never accepted as a portal link (e.g. `/nominate`) or the other way round.
  - **Done:** the Steward Approve path calls the acceptance logic in-process (`acceptProposal()` in `api/_accept_proposal.js`) after the bot has verified Discord's signature and checked `isSteward`. The public `/api/accept-proposal` endpoint, which took the bot token as a password, is gone; the bot token is only used to talk to Discord.
  - **Done:** Approve answers Discord at once with a deferred update (type 6), then saves and edits the message through the click's interaction webhook (its own token, valid 15 minutes; never the bot token), so slow Gist calls can't exceed Discord's 3-second limit. Work after the answer is kept alive with Vercel's `waitUntil` (`api/_after_response.js`, the same hook `@vercel/functions` uses, without that package and its dependencies). If `waitUntil` or the click's id/token is missing, it saves first and then answers, as before. Reject saves nothing and answers straight away.

- **Registering an alliance server (`/registerbot`, `api/register-alliance.js`, 2026-11-11):** the alliance is fixed by the signed link (no tag to type or pick), which `/registerbot` only gives to an `@R5` holding their alliance role in the NAP server (or a Steward). The link carries their Discord id, and before anything is saved or deployed the server checks (`api/_register_checks.js`) that: the bot is in the target server; the person owns it or has **Administrator** or **Manage Server** there (Stewards may register for an alliance without this); the alert and officer channels and the alert role are in that server; and the server isn't linked to another alliance. Delegated role names that match no role there are saved with a warning (the role may be made later). Links made before this update have no id and must be made again.

## Alliance Dashboard (`portal/dashboard.html`, `api/dashboard.js`)
- **Purpose (owner & maintainer spec, 2026-11-11):** each NAP alliance gets a page where its leaders share charts and tables, run a Caravan Rotor, and see their weekly reward status. Built in four steps: foundation (done), widgets, Google Sheets/Docs sync, Caravan Rotor.
- **Who sees what (enforced on the server, never only hidden in the page):** the login pass decides. Members of an alliance see only what its leaders marked for all members (`visibility: "members"`); R4, R5 and alliance officers see everything, including the officers-only reward card; Stewards see everything for any alliance, with a "View as" switcher. No login: asked to sign in. Signed in but no alliance found: told how alliances are found (NAP role or a `[TAG]` nickname). Linked from the header pill card ("🏰 Alliance Dashboard") for signed-in members of an alliance and Stewards.
- **Officers-only reward card (kept small for phones, owner decision):** four short lines: the reward period (open/closed, time left) with a Kingdom War tag (Off-Week / pending / won / lost); the chests as coloured icons with counts, set 1 then set 2 (greyed "if won" while pending; chest names in the tooltips); whether the alliance's list was sent; and a buyout line only when one applies. **Only R5s and Stewards** get a button that opens the nomination page (owner decision: the dashboard makes the same signed link `/nominate` gives); R4s and officers are pointed to their R5 or `/nominate`.
- **Storage: one Gist file per alliance** (`dashboard-<TAG>.json`, tag in plain letters: `RÂVN` -> `RAVN`; owner decision). Every Gist read downloads all files, and GitHub cuts off any file over 1 MB in reads, so one shared file would slow every page and eventually break. Each file is capped (`MAX_DASHBOARD_BYTES`, 150 KB) and holds `widgets`, `settings`, and `tickets` (kept for a later help-ticket feature). Saves go through `updateGist` like every other.
- **Charts and tables (widgets, step 2):** leaders (R4/R5/officers, and Stewards for any alliance) use **Edit Dashboard** to add, edit, move and delete widgets. A widget has a title, an optional explanation, who can see it (🔒 officers only, the default, or 👥 all members) and a table pasted from Google Sheets/Excel (tabs) or CSV, header row first. Types: **bar** (a best-first leaderboard, or vertical bars), **line** (each number column a line; the chart spans the data's own range so growth shows), **pie/donut** (the 7 biggest, the rest as "Other"), **progress** (each row against one target or a column of targets, with "X of Y reached the target") and **table** (search, sort by any column, optional highlight above a value). Numbers can be written as 15,000,000, 15M, 1.2B, 50K or 45% (also in the target and highlight boxes). Charts are drawn in the page (`js/dashboard-widgets.js`, SVG/HTML, no outside library) in the theme's colours (`.dw-s0`…`.dw-s5`; Sanctuary swaps in a blue and a green because its accent is already gold); axis labels are ordinary text so they stay readable on phones. The server cleans every widget (`cleanWidget` in `api/_dashboard.js`: known fields only, text trimmed) and enforces the limits: 20 widgets, 500 rows, 12 columns, 100 characters per cell, 150 KB per alliance. Edits are saved with `updateGist`, so leaders editing at the same moment don't lose each other's changes.
- **Stacked bars (owner request, 2026-11-11):** a bar chart can stack its ticked columns, as *totals* or *to 100%* (each bar split into shares; the axis reads 0–100%), horizontal or vertical. Stacked bars keep the sheet's row order (a side-by-side leaderboard still sorts best first); with more than 8 rows a vertical chart turns into horizontal rows on phones (under 600 px wide). A legend names the columns; each segment's tooltip shows the player, the column and its value (plus the share). **🚦 Traffic-light colours** (`options.scale`, owner request 2026-11-12) replace the theme palette with red → yellow → green (low → high) for clarity: across the columns in order (first red, last green, in-between shades for more columns, e.g. under 3.6M / 3.6M+ / 7.2M+), or for a single column each bar by its size (biggest green). Progress charts can use it too, each bar by how close it is to the target (100% and over green). The three colours are softened and mixed 15% with the theme's accent, so they still sit in Plague, Sanctuary and Miasma. **↕️ Reverse** (`options.reverse`) flips it for numbers where low is good (troops lost, deaths): smallest green, biggest red. Two reading rules help with real sheets: a blank heading after a named one (a merged cell) becomes "name (2)", and a count written `2/16` is read as 2.
- **Tap to read, like the map (owner request, 2026-11-11):** chart parts behave like territories on the map. Hovering one (desktop), tapping it (phone) or Tab + Enter gives it the map's kind of highlight (a bright outline, a glow and a little brightness, as in `setHighlightedTerritory`; nothing else fades) and fills the map's own info card (`.info-card`) under the chart: a badge with the part's value, the name, then "Column: value" items. **The highlight takes the selected part's own colour** (owner request, 2026-11-12): a red segment glows red, and the card's stripe, badge and bold item match it; a part made of several colours (a whole stacked row, a line-chart week) uses the theme colour. Phones' grey tap flash is switched off on chart parts. Pie and donut slices are drawn as shapes (ring segments or wedges), and a selected shape in a drawing is copied on top of the others (like the map's highlight overlay), so pie slices get the same outline and glow as bars, unclipped. Moving the mouse off clears it, as on the map; a tap or click keeps it until it's tapped again, Escape, or a tap outside the chart. Bars list every column of their row (stacked to 100%: the shares plus the cells as written; totals: each value with its share of the bar, and the total; single bars: the value and its share of the column's total, unless the column is already a %); tapping a name selects the whole row. Pie slices and their legend rows light up together and show the %, the value and the total; progress rows show value of target and what is left; a line chart has one tall tap area per row (its dots are too small for fingers) with every line's value and its change since the row before. The card shows one more decimal than the chart (1.26B). Axis labels gain decimals when the range is narrow, so two labels never read the same.
- **Google Sheets / Docs (step 3):** a widget's data can come from a link instead of a paste. In the editor's **🔗 Google Sheet / Doc link** tab a leader pastes the link (Sheets: optional tab name and range like `A1:D20`; Docs: which table) and presses **Load**; the server reads it and the preview fills. Saved cards show "🔗 Google Sheet · synced …" and leaders get **🔄 Sync now** to fetch the latest numbers (the old ones stay if Google refuses). Sheets must be shared "Anyone with the link can view" or published to the web; Docs published to the web. The server (`api/_google_source.js`) only fetches Google's own addresses: `docs.google.com`, and the `googleusercontent.com` hosts its downloads redirect to, checking every redirect itself (a redirect elsewhere is refused, never fetched; one to Google's sign-in page means "not shared"). 8-second timeout, 2 MB cap, the same table limits as pasted data. Members can't make the server fetch anything.
- **Caravan Rotor (step 4):** a card run by the alliance's R4/R5s and officers (and Stewards): a roster of players, each with an optional Game Time window (`18:00–22:00`, or a single time; empty = flexible), shown with the reader's own time beside it. Leaders add, edit and remove players, tap **✓ Picked** when a player gets a caravan (time and officer recorded; if two officers tap the same player, the first pick stands), **Undo** a pick, and **🔄 New week** (everyone available again, names and times kept). **⏰ Around now** shows who is available at this hour (plus flexible players); **📋 Copy status** copies a summary for Discord or in-game chat. No member sign-ups (spec). **👥 Members can view** lets members see the rotor read-only; the server sends it to members only then, and without which officer picked whom. Stored in the alliance's dashboard file (`caravan`), at most 100 players.
- **Merging lists with ids:** when saves clash (`updateGist`), lists whose items have an `id` (widgets, rotor players) are merged item by item, so two officers changing different players both count and nothing is duplicated; new items get their id once, in the endpoint, so a repeated save replaces rather than adds.
- **Vercel Hobby plan: 12 functions at most.** The dashboard API is the 11th; `/reset` became a plain page to keep one slot free. Prefer adding to an existing endpoint over a new one.

## Alliance defaults (`_data/alliances.yml`)
- **One list:** the alliances the code knows before live data loads (fallback colours, which `DISCORD_<name>` setting holds each alliance's NAP role ID, the starting Capitol rotation) live only in `_data/alliances.yml`. The build turns it into `api/_alliances_data.js` (server) and `js/alliance-defaults.js` (browser); both are generated and git-ignored. The three cycles' starting schedules are worked out from the starting seats by the same wheel as the rotation (`api/_cycle_helper.js`). Never copy these values into code again.
- **Alliance colours, one order everywhere (fixed 2026-11-12):** an alliance's colour is its **NAP role colour in Discord**, then a colour chosen on the site (the gold `#b8975a` counts as none), then `_data/alliances.yml`. The server applies this order itself (`sanitizeAlliances` with `getRoleColors` from `api/_role_colors.js`), so `/api/state`, `/api/calendar` and `/api/dashboard` all send the same colour, and every page (calendar, King's console, rewards, dashboard) matches the Alliance page and map. Before, only the Alliance page and map asked Discord, so WLO (light blue in Discord, no colour saved) showed the green default elsewhere. Role colours are read from Discord at most every 10 minutes per server instance, with a 2.5-second limit; if Discord is slow or down, the last known colours (or the saved/default ones) are used. `/api/colors` still answers for the Alliance page and map, from the same helper.
- **No built-in snapshots:** the map, the alliance page and the rewards card show the live data only (`/api/state`). The old page snapshots (`_data/map_state.yml`, `_data/diplomacy.yml`, the tiers in `_data/rewards_data.yml`) were removed: they were a hand-kept second copy that went stale and was shown, unmarked, whenever live data failed. Now a page says "Loading…" until the data arrives, and says plainly when it couldn't load (`js/live-data-notice.js`). Planner Mode, Edit Blacklist and the rewards planner don't start without live data, so a plan can never be built on an empty page. `_data/rewards_data.yml` keeps only the weekly pool (a game constant).
- **Offline:** the service worker (`sw.js`) fetches `/api/state` and `/api/calendar` fresh when online and keeps the last good answer; offline, pages show that copy with a notice ("Offline: showing the data saved on this device (date)", from its `X-Offline-Copy` header).

## Data storage (GitHub Gist as database)
- **Purpose:** Stores live mutable state (`map-state.json`, `rewards-data.json`, `rewards-nominations.json`, `calendar-state.json`, `proposal-log.json`: who sent a proposal when, last 24 hours only, for the daily limit; and `last-save.json`: which revision the latest save was worked out from and which files it wrote, used by `updateGist`) without requiring an external database server.
- **Constraints:** All state files reside in a single GitHub Gist (`process.env.GIST_ID`), fetched in one HTTP request.
- **Must not change:**
  - `map-state.json` is the single source of truth for alliance ranks (`#1`–`#10`).
  - All Gist reads and writes go through `api/_gist.js` (`readGist`, `gistJson`, `updateGist`). Endpoints must not call the GitHub API directly.
  - **Every save goes through `updateGist` (safe saves).** The save is written as a function that works the change out from the data it is given; `updateGist` reads, saves, then checks the Gist's revision history: the revision just before ours must be the one we worked from. If other saves landed in between (two alliances nominating at once, a nomination during the Won/Lost result, two approvals), ours overwrote them, so it rebuilds from the latest data: each overwritten save's own change is put back (the files it wrote compared with the revision it started from, both recorded in `last-save.json`, merged field by field by `mergeJson`), our change is taken out and worked out again on top, and it saves and checks again. Every save repairs what it overwrote, so all changes are kept. Up to 6 rounds with a short random pause, stopping after 8 seconds (or the caller's `deadline`); a warning is logged if it ever gives up. GitHub can't refuse a save on conflict, so this is a repair afterwards, not a lock: for a moment the Gist can show one save without the other. Use `writeGist` directly only for something that isn't worked out from stored data (e.g. `/devupdate`'s copy). Tested with a fake Gist keeping real revisions: two, three and six saves at once, with realistic delays.
  - **Write paths never fall back to defaults.** If the Gist can't be read, a write or mutation (approvals, nominations, events, registration, cycle resets) stops with an error and saves nothing; continuing with `{}` would wipe live data. Defaults are only used when a read succeeds but the file doesn't exist yet. Read-only endpoints (`api/state.js`, `api/calendar.js`, `api/map-image.js`) may fall back to defaults so pages still render.
  - **A failed save is never hidden.** E.g. if the automatic Downtime reset in `/nominate` can't be saved, the leader gets "Service busy … retry" instead of a nomination link.
  - Each save sends only the Gist files it changed (`writeGist` only sends what it is given), plus `last-save.json`.
  - **The test site never touches live data.** dev.la-s78.app is a Vercel *preview* deployment (`VERCEL_ENV=preview`): it uses `TEST_GIST_ID` (a separate Gist) and nothing else; without it, it has no data rather than falling back to `GIST_ID`. Its proposals post to `TEST_CHANNEL_ID`, marked "🧪 TEST", and the live bot refuses to approve them (the bot's endpoint is always the live one). `/devupdate` (owner server, Stewards only, private replies) refreshes the test data: the live bot copies every live file into `TEST_GIST_ID` (`copyLiveGistToTest` in `api/_gist.js`; it only reads the live Gist and refuses if the two are the same). It runs on the live site because Vercel never hands out values marked Sensitive to anything else (a GitHub Actions copy job was tried and removed for that reason), so `TEST_GIST_ID` is set for Production as well as Preview, and no secret is stored outside Vercel.
- **Open questions:**
  - Every write reads, changes and saves the whole file with no check for a concurrent change, so two simultaneous writes can lose one. Is that acceptable at current usage?
    **Answer (maintainer, 2026-11-11):** acceptable for most files at current usage, but not for the shared ones. `rewards-nominations.json` holds every alliance's list, and each nomination also saves `rewards-data.json`, which the Saturday Won/Lost result rewrites, so two saves close together can lose one. **Done:** every save now goes through `updateGist` (see "Every save goes through `updateGist`" above).

## Rewards, nominations & KvK cycle
- **Purpose:** Automates the 4-week Capitol rotation, stepped defense overrides (Swap vs. Wartime Buyout), and weekly chest nomination quotas.
- **Constraints:** No background cron exists; cycle and reward transitions rely on deterministic clock math (`_calendar_helper.js`) and lazy synchronization triggered by Discord interactions.
- **Must not change:**
  - **Option A (4-Week Lock + Seat Inheritance):** `active_schedule` locks for the 4-week cycle (`downtime`, `week_1`, `week_2`, `week_3`). Rank #1 holds `week_3`. The three non-#1 alliances in Top 4 rotate through `[Seat A, Seat B, Seat C]` across 3 macro cycles so no alliance serves Downtime twice in a row. If a Rank #5+ contender enters the Top 4 (measured during Week 1 Duel Days 3–5), they inherit the vacated wheel seat at the start of the *next* 4-week cycle.
  - **Stepped Defense Overrides (Model 1):** 1st WLO override in a cycle swaps calendar weeks with Week 3 (0 chest cost). 2nd WLO override triggers a 2-installment Wartime Buyout (+1 Reg Gold & +1 KW Gold in target week, +1 Reg Gold & +1 KW Gold in Week 3, deducted from WLO and added to the displaced alliance). "Reg Gold" is set 1's gold chest, **Commander's Will**; "KW Gold" is set 2's gold chest, **Honor Vanguard**, so it is paid only when that week's Kingdom War is won (see below).
  - **Reward periods (owner rule, written down 2026-11-10):** every week has one reward period. It opens at the Friday capitol event (**Friday ~20:00 GT**) and closes when the game expires the chests (**Wednesday 00:00 GT**, i.e. the end of Tuesday of the next week). The period belongs to the week its Friday is in (week N), also on Monday/Tuesday of week N+1: its schedule holder and its buyout installments. Between Wednesday 00:00 and Friday 20:00 nothing is open. `api/_reward_period.js` (`getRewardPeriod`) works this out from the clock; there is no background timer, so the stored state moves on (`syncRewardPeriod`) the first time `/nominate`, `/rewards`, a result button or a saved list touches a new period.
  - **Two sets of chests (in-game names):** set 1, **King's Commendation** (Commander's Will, Loyal Servant, Follower's Heart), every week including the off-week. Set 2, **King of Battle Reward** (Honor Vanguard, Fearless Hero, Logistics Support), only after the server **wins Kingdom War** (invasion rights and the battle; shown simply as "won"). The King's Crown and Mythic God of War chests are the King's own and are not nominated.
  - **Kingdom War result:** recorded by a Steward (Won / Lost) because the site can't see the game. The battle starts Saturday 12:00 GT and usually ends by about 14:00 GT; from then the bot asks NAP Leadership once (buttons), and `/rewards` Won/Lost does the same. It can be changed both ways until the period closes; every list is then re-sorted, with a "check with the King" warning because chests already handed out in the game can't move. `isKW` is strictly `mode === 'kw'`, set only by a recorded win (never guessed from the week number). The bot answers Discord at once and fills in the message when the save is done (as Steward approvals do), so the save has time for every safe-save round.
  - **Nominations are a ranked list (owner decision):** each alliance saves one list of players, best first (`rewards-nominations.json` `ranked`); the chests are always worked out from it (`api/_nomination_assign.js`) in value order: Honor Vanguard → Commander's Will → Fearless Hero → Loyal Servant → Logistics Support → Follower's Heart, one chest per player. Names beyond the chests are reserves and move up when more chests open. So a win (or a correction) re-sorts the same list and the best players still get the best chests. Every saved list re-sorts all the lists from their names, so all chests always match the stored result, even when a list and the result were saved at the same moment.
  - **King's checklist (owner decisions, 2026-11-11):** chests ticked as handed out on the King's console (`/distribute.html`) are saved with the period (`rewards-data.json` `period.handed_out`), so every device sees them; a new period (or a Steward's `/rewards reset`) starts a fresh checklist. Ticking is for the **R4/R5 of the King's alliance** (the one scheduled to hold the Capitol in the period's week, `active_schedule[slotKey]`, swaps included) **and Stewards**; everyone else sees it read-only. **A ticked chest is locked:** it was given in the game, so it stays with that player through any re-sort (Won/Lost or a correction, the alliance re-sending its list, even without that player), and the rest of the list is sorted around it (`assignChests` in `api/_nomination_assign.js`). A tick stands even if the list was re-sorted at that moment (the lock pulls the player back into that chest); only a player no longer on the alliance's list is refused. One chest per player: a tick for another chest replaces the old one. Ticks can be undone by the same people. **Copy checks first:** a name copied on the console is checked against the latest lists straight after copying; if the alliance changed or removed it (or it now gets another chest), the console says "Stop: don't send that …", refreshes the lists, and shows an alert, before the chest can be sent in the game. The alliance's nomination page shows its handed-out players as locked, outside the editable list.
  - **Hold until the result (owner decision):** in a Kingdom War week the King waits for the battle result (about Saturday 14:00 GT) before handing out set 1, so nobody's chest changes after it is given. In the off-week set 1 is handed out straight away.
  - **Switch-over:** the first run adopts the open period as it is (lists already sent stay; a week already marked won stays won), and a period change never advances the rotation onto the week it is already on. Buyout installments still pay their set-2 chest only when that week is won.

## Calendar & event management
- **Purpose:** Displays the 28-day Kingdom War & Capitol rotation cycle alongside global and alliance-scoped operations (`calendar.html`, `/calendar`).
- **Page type (owner decision):** a regular page with the footer, like Map and Alliance (everyone reads it; leaders get extra controls), not a portal page. Its styles come from `/css/portal.css`, linked inside the page so they apply only there. Its scripts start once per visit, whether reached by a full load, the footer, or the back button, and the countdown stops when the page is left. Discord links (`/calendar.html?token=…`, `?view=…`) are unchanged.
- **Constraints:** `_calendar_helper.js` numbers calendar weeks `1..4` in the order `capitol_rotation` lists them (by default the Off-Week is `4`, but `calendar-state.json` in the Gist can put it anywhere, e.g. first). `rewards-data.json` and `kvk-scheduler.js` use the seats `downtime` (`0`), `week_1`..`week_3`.
- **One conversion only:** `getScheduleSlot()` in `_calendar_helper.js` turns a calendar week into a seat: the week marked `is_kw: false` is `downtime`, and the Kingdom War weeks count up from 1. `getCycleState()` returns the result as `clockWeek` and `scheduleSlot`. The website and the bot must use these, never their own rule such as "week 4 is downtime" (that rule made the hero card and the console disagree with the phase name when the live calendar started on the Off-Week).
- **Week names (owner):** the off-week is called **"Off-Week"** everywhere people read it (site, Discord), never "Downtime" or "NAP Rest Week"; Kingdom War weeks are "Kingdom War Week 1..3". Use `weekLabel()` / `getCycleState().weekName`, not the configured `phase` text (the Gist's `calendar-state.json` may still hold old names). `downtime` stays only as the internal key of the reward schedule.
- **Week and capture day (owner):** event weeks run Monday to Saturday, and the week's alliance captures the Capitol on **Friday** (`capture_day_of_week: 5`). `getCycleState()` returns `capitolCaptured`, `isCaptureDay` and `captureTimestamp`. Before the capture the hero card and `/calendar` say "Next Capitol Holder … captures Friday"; afterwards "Current Capitol Holder … captured Friday". The timeline's "Capitol Capture" entry is on the Friday, never on the Monday reset.
- **Must not change:** Both the Top Hero Card (`api/calendar.js` / `js/calendar.js`) and the 4-Week Override Console (`js/kvk-scheduler.js`) must resolve the active Capitol holder from `rewards-data.json`'s `cycle_state.active_schedule` and highlight the active week using the live clock (`clockWeek`), never static `capitol_rank` lookups alone.

## Conventions
- **Game Time is UTC-2.** All schedule/calendar code and bot strings use this.
- **Pull requests** must pass the "Checking build output" CI step before merge.
- **Deploys never overlap.** The workflow's `concurrency` setting runs one deploy per branch at a time; a newer push waits rather than racing, so the newest commit always deploys last. Don't remove it.
- **Folder layout.** Discord tool pages (single-purpose, opened from a Discord link, no footer) live in `portal/`, and their public URLs come from each page's `permalink` (e.g. `/calendar.html`), not from the folder. Files used only by the deploy (`redirect.html`, `migration.html`) live in `_deploy/`, which Jekyll never publishes. Keep public URLs unchanged when moving files.
- **Stylesheets are split into ordered pieces.** `_css/<name>/*.css` is joined in filename order into `/css/<name>.css` by `build.rb` (plain CSS, no Sass). Order is significant (later rules win), so pieces are numbered and media queries come last. The published URLs `/css/style.css` and `/css/portal.css` must not change.
- **One build script.** `_scripts/build.rb` is the only build definition; CI calls it rather than running its own inline steps, so a local build matches production. New build steps go in the script, not in the workflow.
- **Code style is automatic.** JavaScript and JSON are formatted by Prettier (`.prettierrc.json`: defaults plus single quotes and 100-character lines). Don't hand-format or argue style in reviews; run `npm run format` or use format-on-save. HTML/Markdown/YAML are excluded because of Liquid tags. The CI formatting check is advisory, not blocking.
- **Page scripts and Turbo.** A page's script must start only when its own section is on the page, and once per visit: keep the started section elements in a `WeakSet` (not a `data-` attribute, which Turbo's back-button copy of the page keeps). When a script starts on a fresh section, it first clears leftover `data-bound` marks inside it, because a fresh section can be that back-button copy. Inline `<script>`s run again on every visit, so they must not declare top-level `const`/`let`. `js/map.js`, `js/alliance.js`, `js/rewards.js`, `js/calendar.js` and `js/kvk-scheduler.js` follow this.
- **Theme colours (owner decision).** The three themes change one colour family, `--active-theme*` (set per theme in `05-base-variables-themes.css`). The accent (`--accent-color`), borders (`--border-color`) and surfaces (`--bg-color`, `--nav-bg`, `--card-bg*`, `--surface-*`) mix that theme colour into the original gold and browns: 70% for the accent, 30% for borders, 6–8% for surfaces (the owner compared four strengths and chose this one, "3c"). Text and fixed meanings don't follow the theme: status red/green, rank colours, chest tiers, alliance colours, Discord blue. Where gold means *gold* (the gold chest tier, the #1 row of the alliance ladder), use `--gold`, not `--accent-color`.
- **See-through colours use `color-mix()`.** A transparent version of a colour that has a variable is written `color-mix(in srgb, var(--accent-color) 20%, transparent)`, not `rgba(184, 151, 90, 0.2)`, so changing the variable changes every use. Use whole percentages. Variables that already include transparency (`--card-bg`, `--status-danger-bg`, `--status-success-bg`) can't be mixed this way (the two transparencies would multiply), so their other strengths stay as `rgba()`. Measured against `rgba()`: identical pixels (192 colour/strength/background combinations).
- **White and black overlays and shadows use a fixed scale.** `--overlay-3/5/8/12/25` (white) and `--shade-30/40/50/60/70/80/95` (black) in `05-base-variables-themes.css` are the only strengths for see-through fills, borders and shadows. Pick the nearest step instead of writing a new `rgba(255, 255, 255, 0.07)`; add a step only when a new strength is really needed.
- **Generated files are git-ignored** (see `.gitignore` and the README's "Never edit these" list) so local builds never show up as changes.
